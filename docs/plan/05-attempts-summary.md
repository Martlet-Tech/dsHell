# 05 · 添加工作区不刷新：历次尝试汇总

> **性质**：复盘台账，不是升级项。立项推导在 `04-workspace-add-no-refresh.md`。
> **目的**：把十几轮尝试压成一张表，避免重复走死路。
> **记录时间**：2026-09-12

## 1. 现象

DShell 里点侧边栏「工作区」的 `+` → 选文件夹 → **点确定**之后，界面不刷新。

**关键特征（用户实测，2026-09-12 补充）**：

| # | 特征 | 含义 |
| --- | --- | --- |
| C1 | 之后**点窗口内任何地方**都能触发（侧边栏、聊天区、**甚至标题栏**） | 不是某个按钮的事件 |
| C2 | **不点就永远不跳** | 每次必现，不是偶发 |
| C3 | 命令行 `dsh web` + 浏览器里做同样操作，**秒完成** | 差异只在 DShell 环境 |

> C1 是最有价值的线索：**标题栏不是网页内容**，点它也能触发，
> 说明触发点在**窗口/输入层**，不在页面层。

## 3. 探针已经证明的事（确定结论）

| 结论 | 证据 |
| --- | --- |
| **渲染没有停摆** | 全程 `gap`（帧间隔>100ms）只有 1 次，且发生在页面初载；对话框开着期间**零掉帧** |
| **页面焦点正常归还** | `hasFocus=false` 每次只持续 **1–2ms** 就回到 `true` |
| **前端没有报错** | 无 `js:error`、无 `console.warn`、无 `unhandledrejection` |
| **DOM 变化是即时的** | 观测到的几次操作里，`mousedown` → `dom:added` 间隔约 **24ms** |

**推论**：页面层（渲染 / 页面焦点 / JS 状态链）**全部正常**。

> `initialization_script` 在本项目**不生效**——这条对将来任何"往 DSH 页面注入"的需求都成立。

### 3.1 一个曾长期误导判断的假象

探针日志里反复出现这个模式（三次运行、完全一致）：

```
12072ms  blur   hasFocus=false     ← 判定为"对话框关闭"
12074ms  focus  hasFocus=true
12076ms  mousedown el=div.wSkVaW_composerSeat   ← 一度被当成"用户点空白"
12100ms  dom:added 『fpv-taobao』   ← 工作区出现
```

`blur` 与 `mousedown` 只隔 **4ms**。若用户真的"数了 5 个数再点"，这里应是 5000ms+。
**唯一自洽的解释**：这两条是**同一次物理点击**的两个回声——用户按下的那一下落在文件对话框上，
对话框关闭后同一个鼠标事件被转发到底下的 DShell 窗口，于是页面先看到 `blur` 再看到 `mousedown`。

**教训**：不能把"页面收到的 `mousedown`"等同于"用户新点了一下"。
在窗口/对话框边界上，一次物理点击可以在页面日志里出现两次。

## 3.2 用户实测：哪些输入能触发（关键线索）

用户在对话框关闭后逐个试（2026-09-12）：

| 输入 | 能否触发刷新 |
| --- | --- |
| 点**别的软件**（切走再回来） | ✅ 能 |
| 按 **Tab** | ✅ 能 |
| 按 **Alt** | ✅ 能 |
| 按 **Ctrl** | ❌ **不能** |
| 按 **CapsLock** | ❌ **不能** |

**规律**：能触发的输入都会**改变窗口激活 / 焦点状态**（Tab 走焦点遍历、Alt 进系统菜单模式、
切走再回来改变前台窗口）；不能触发的（Ctrl、CapsLock）都是**纯修饰/锁定键，不改变窗口状态**。

### 3.3 用户实测：悬停与 tooltip 的异常（决定性线索，2026-09-12）

用户在"异常态"（对话框已关闭、但界面没刷新）下观察到的两个现象：

| # | 现象 | 说明 |
| --- | --- | --- |
| H1 | 发送消息按钮 **鼠标悬停没有 hover 变色** | 正常时有；异常态时没有 |
| H2 | 「添加工作区」按钮的 tooltip **卡住不消失** | 鼠标已移开，tooltip 仍留在原地 |

**这两条指向同一件事**：

| 现象 | 依赖什么 | 缺失说明 |
| --- | --- | --- |
| H1 无 hover 变色 | CSS `:hover` → 需要 `WM_MOUSEMOVE` 到达 WebView | **鼠标移动事件没有送到页面** |
| H2 tooltip 卡住 | `mouseleave` + 延时定时器 | **事件处理与计时器都停了** |

**关键区别**：鼠标本身能移动、光标形状也正常 → 说明**窗口是活的、系统层鼠标消息正常**；
但 **WebView 内部既不处理 `mousemove`、也不跑定时器**。

> **推论修正**：这不是"Windows 窗口未激活"（§3.2 的推论），
> 而是 **WebView2 的渲染进程被挂起（frozen / suspended）**——
> 页面成了"僵尸"：DOM 还在、点击能进（唤醒），但**事件分发与定时器全部停摆**。

### 3.5 R6 实测：冻结**已被证实**（决定性证据，2026-09-12）

R6 探针改用**双时钟 + 定时器推进**做判据（不再依赖页面时间戳，见 §3.4）：

- 页面每 250ms `setInterval` 打点，同时记录 `ticks`
- 每 5s 发一次 `heartbeat`
- **Rust 侧给每条回传加墙钟戳** `[HH:MM:SS.mmm]`，作为权威锚点

实测结果：

| Rust 墙钟 | 页面 `t=` | `ticks` | 说明 |
| --- | --- | --- | --- |
| 09:08:43.350 | 5055ms | 20 | 正常 |
| **09:08:58.360** | 10061ms | 40 | 墙钟过了 **15.0 秒**，但只 tick 了 20 次（=5 秒的量） |
| **09:08:58.362** | 15061ms | 60 | **2 毫秒后** |
| **09:08:58.363** | 20056ms | 80 | **再 1 毫秒后** |
| 09:09:03.352 | 25057ms | 100 | 恢复正常 |

**三条心跳在 3 毫秒内全部到达，而它们的页面时间戳相差 5 秒、5 秒。**

⇒ 那 10 秒里 `setInterval` **一次都没跑**，解冻后**积压的周期被一次性补发**。

**结论：页面（渲染进程）确实被冻结了约 10 秒**，与用户"过了几秒"的描述完全一致。

### 3.6 最终因果链

1. 点「添加工作区」→ dsh 弹出原生 `IFileOpenDialog`（独立子进程，抢走前台焦点）
2. WebView2 把 DShell 窗口判定为**被遮挡的后台窗口**（Chromium 的
   `CalculateNativeWinOcclusion` 遮挡计算）
3. 触发 **Page Lifecycle 的 `frozen` 态** → 渲染进程停止执行：
   定时器停摆、事件不分发、React 不提交
4. 对话框关闭后，**没有任何东西触发 `resume`** → 页面保持僵尸态
5. 用户产生**任意一次输入**（点击 / Tab / Alt / 切走再回来）→ 浏览器唤醒渲染进程
6. 积压的工作一次性执行 → 工作区出现并跳转

**这一条链解释了此前所有看似矛盾的现象**：

| 现象 | 解释 |
| --- | --- |
| "过了几秒"vs 日志 3ms | 冻结期间页面时钟不推进，时间戳挤在一起（§3.4） |
| 点击才刷新 | 输入事件唤醒渲染进程 |
| hover 不变色、tooltip 卡住 | 冻结期间事件分发与定时器全停（§3.3） |
| Ctrl/CapsLock 无效、Tab/Alt 有效 | 前者不产生唤醒所需的输入事件流 |
| 浏览器里正常 | 浏览器标签页有自己的生命周期管理，且浏览器窗口本身是前台 |
| 早先两个"禁节流"开关无效 | 它们治的是**节流**（降频），不是**冻结**（完全停止），且未触及遮挡判定源头 |

### 3.4 页面时间戳为什么不可信

前面几轮反复出现"`blur` 与 `mousedown` 只隔 3–4ms"，与用户"过了几秒"的描述矛盾（§3.1）。

若 §3.3 的"渲染进程被冻结"成立，则**矛盾自动消解**：

- `performance.now()` 在渲染进程被冻结期间**不推进**（或推进与墙钟脱节）；
- 页面被唤醒后，积压的事件**一次性补发**，因此时间戳挤在一起。

**结论：页面内的时间戳不能作为墙钟证据。** 后续探针必须：
1. 同时记录 `Date.now()`（墙钟）与 `performance.now()`，两者对照；
2. 用 **`setInterval` 是否推进**作为"页面是否被冻结"的二值判据（无解读空间）；
3. 用 **Rust 侧墙钟**做权威锚点。

> §3.2 的"窗口未激活"推论**已被 §3.3 取代**——能触发的输入（Tab/Alt/点击/切窗口）
> 共同点不是"改变窗口激活态"，而是**能产生一次输入事件把渲染进程唤醒**。

### 3.7 R7 实测：加了防冻结开关仍然不好使（2026-09-12）

**改动**（`main.rs` 的 `additional_browser_args`）：

```
--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection,CalculateNativeWinOcclusion
--disable-backgrounding-occluded-windows
--disable-renderer-backgrounding
--disable-background-timer-throttling
```

**结果**：

| 观察 | 修复前（R6） | 修复后（R7） |
| --- | --- | --- |
| `freeze` 事件 | 有 | ✅ **0 个** |
| 定时器准点 | 否（15 秒只 tick 20 次） | ✅ **准点**（每 5 秒 20 tick） |
| **界面自动刷新** | ❌ | ❌ **仍需点一下** |

**结论：冻结被消除了，但现象依旧。** ⇒ **"页面冻结"不是根因，只是同一底层问题的另一个症状。**

> 这三个开关**有实效**（冻结确实没了），值得保留；但它们不解决本 bug。

### 3.8 R7 的关键新线索：合成的 Alt 被扣押

R7 日志里发现一条用户**没有按过**的按键：

```
keydown Alt    t=7840ms    →  Rust 墙钟 09:15:38.911
blur           t=14316ms   →  Rust 墙钟 09:15:38.920
```

**这是 dsh 自己合成的 Alt**：`win32-dialog-logic.ts:134` 的
`pressAltForForeground()` —— 在 `dialog.show()` **之前**用 `keybd_event`
合成一次 Alt 按下+抬起，目的是抢前台（注释说明：Windows 只把前台权给
"前台进程 / 它启动的进程 / 最近有输入的进程"，而后台宿主一个都不满足）。

**异常之处**：`t=7840ms`（对话框开启前）的事件，直到 `09:15:38.911`
（对话框关闭时）才送达 Rust —— **积压了约 2.5 秒**。

⇒ **合成的 Alt 一直扣押在消息队列里，直到对话框关闭才投递。**

### 3.9 当前假设：Alt 污染导致窗口停在"待复位"状态

`keybd_event` 合成的是**系统级真实按键**。对话框关闭时，那个 **Alt-Up**
被投递给 DShell 窗口，而 **Alt-Up 在 Windows 中表示"系统菜单模式结束"**，
可能让窗口进入需要额外输入才能复位的状态。

这与用户的输入规律**完全吻合**：

| 输入 | 能否触发 | 是否涉及系统菜单/激活复位 |
| --- | --- | --- |
| Tab | ✅ | 是（焦点遍历） |
| Alt | ✅ | 是（系统菜单模式） |
| 点击（含标题栏） | ✅ | 是（取消菜单模式） |
| 切走再回来 | ✅ | 是（前台窗口变更） |
| **Ctrl** | ❌ | 否 |
| **CapsLock** | ❌ | 否 |

**用户原话："不点肯定不出现。"** ⇒ 窗口停在**等待一次输入来复位**的状态。

> **状态**：假设，尚未验证。验证方式见 §6。

### 3.10 R8：窗口消息层探针（已构建，待实测）

前七轮全在**页面层/渲染层**取证，而这一层已经查清（C1）+ 修好（C5）。
R8 第一次把探针下沉到 **Windows 窗口消息层**——也就是 §6 表格里
唯一标着"从未测过"的那一格。

**实现**：`src-tauri/src/winprobe.rs`，用 `SetWindowsHookExW(WH_GETMESSAGE)`
挂**进程内**钩子（`dwThreadId = 0` 挂调用线程，不需要 DLL 注入），
只读地抄一份流经 UI 线程消息队列的消息。

| 抓什么 | 回答什么问题 |
| --- | --- |
| `WM_SYSKEYDOWN` / `WM_SYSKEYUP` | dsh 合成的 Alt **按下与抬起是否成对**？抬起迟到多久？ |
| `GetKeyState(VK_MENU)` 实时态 | "消息没来"与"状态没复位"是两回事，这一列能分开 |
| `WM_ACTIVATE` / `WM_ACTIVATEAPP` / `WM_NCACTIVATE` | 对话框关闭后 DShell **有没有拿回激活态**？ |
| `WM_SYSCOMMAND` + `SC_KEYMENU`(0xF100) | 窗口是否掉进"系统菜单模式"（Alt 被按下的直接后果） |
| `WM_LBUTTONDOWN` | 与页面 `input:mousedown` 对照 → **消息到达窗口**与**页面收到**之间的延迟 |
| `WM_KEYDOWN` / `WM_KEYUP` | 用户真实键盘输入的时间线 |

**关键设计**：

| 决策 | 原因 |
| --- | --- |
| 钩子回调里**只做两件事**（`GetForegroundWindow` + `GetKeyState`），其余塞无锁环形队列 | 回调跑在 **UI 线程**上，一旦在那里写文件/取锁就等于**探针自己制造卡顿**，现象被污染 |
| 取数线程另有其人，每 100ms 排空 | 时间精度毫秒级够用，且完全不占 UI 线程 |
| `Alt` 物理状态**翻转时自动补一条 `winsnap`** | 把"Alt 何时被复位"从一堆消息里显式拎出来，不用人反推 |
| `WM_MOUSEMOVE` 默认**不采**（噪声极大），留 `set_mousemove()` 开关 | 鼠标一动几十条，会淹掉真正要看的事件 |
| 时间戳复用页面探针的 `stamp()` 格式 | 两路日志 `HH:MM:SS.mmm` **直接对齐**，这是判据成立的前提 |

**依赖**：新增 `windows-sys 0.61`（版本对齐 `Cargo.lock` 已有版本，不重复拉）+ `raw-window-handle 0.6`（tauri 2 **不** re-export 它，必须直接依赖，否则 trait 不是同一个、`window_handle()` 找不到）。

### 3.11 R8 第一次实测：钩子没装上（写错了）；已修正并加固

**实测结果：探针自己就失败了。** 日志第 3 行：

```
[winprobe] SetWindowsHookExW 失败：没有模块句柄无法设置非本机的挂接。 (os error 1428)
```

**我的错**：代码注释里写"`dwThreadId = 0` 会把钩子挂到调用线程，且无需注入"——
**这是错的**。查 Win32 文档：`dwThreadId = 0` 的意思是"**全局钩子，关联所有现存线程**"，
而全局 `WH_GETMESSAGE` 要求钩子过程位于**独立 DLL** 中并经 `hMod` 传入，
传 `null` 必然被拒（`ERROR_HOOK_NEEDS_HMOD = 1428`）。

正确写法是传**当前线程 ID**：

```rust
let tid = GetCurrentThreadId();
SetWindowsHookExW(WH_GETMESSAGE, Some(hook_proc), null_mut(), tid)
```

这才是"只挂本线程、不需要 DLL 注入"的写法。

> **教训（记为 M5）**：写完探针**没有先验证探针自己能跑通**，直接把一轮测试机会交给用户。
> 以后凡是新增探针，必须让它在启动时**自报"我成功了"**（本次已有该行，正因如此才一眼看出失败），
> 并且**用户操作前先看一眼日志第一条探针行**。

#### 顺带发现钩子的结构性盲区（本轮真正的收获）

复盘时意识到：**即使钩子装上了，它也看不到最关键的那种情况。**
`WH_GETMESSAGE` 只在消息**被取出**（`PM_REMOVE`）时回调。
如果窗口真被卡住、消息躺在队列里没人取，钩子**一条都收不到**——
而"没收到"和"没发生"在日志里长得一模一样。**这正是前几轮反复误判的同一个坑**（见 §3.4）。

所以 R8-b 补了一个**独立于消息流**的看门狗线程，每秒轮询：

| 查什么 | API | 为什么它比钩子可靠 |
| --- | --- | --- |
| Alt/Ctrl/Shift **物理**键态 | `GetAsyncKeyState` | 反映硬件此刻状态，**不受消息是否被处理影响** |
| 前台窗口 | `GetForegroundWindow` | 与消息流无关 |
| **队列积压** | `GetQueueStatus(QS_ALLINPUT)` | `qKey=1`/`qMouse=1` = 队列里**还有输入没人取** = 卡住的直接证据 |
| **是否处于菜单模式** | `GetGUIThreadInfo` → `GUI_INMENUMODE`(0x4) | Alt 按下会让窗口进菜单模式，这是**独立状态位** |

这四项合起来，即使钩子完全收不到消息，也能判断"窗口是不是卡住、卡在什么状态"。

**同时也要承认**：`GetAsyncKeyState` / `GetGUIThreadInfo` 读的是**系统全局**状态
（不是本窗口私有），所以只能佐证、不能单独定案。最终判据仍是
"**用户点第一下的那一刻，状态位发生了什么变化**"。

### 3.13 **读源码找到疑似根因：`queueMicrotask`**（2026-09-12 15:20，重大发现）

前 14 轮一直在**测量**（加探针看现象），这一轮改为**读 dsh 源码**追调用链，
结果直接定位到一段**可以解释全部现象**的代码。

#### 调用链（从点击「添加工作区」到界面刷新）

| # | 位置 | 做什么 |
| --- | --- | --- |
| 1 | `WorkspacePicker.tsx:136` `openDirectoryFlow()` | 置 `flowOpen=true` |
| 2 | `ui-directory-picker-native/src/client/flow.ts:53` | `open` 变 true → 调 `pick()` |
| 3 | `directory-picker.ts:55` `@Remote('pick')` | 跨进程弹原生对话框 |
| 4 | `flow.ts:56` `outcome.current.onPicked(path)` | 用户点确定后回调 |
| 5 | `WorkspacePicker.tsx:163` `onPicked` | `setPickingFolder(true)` + `adoptDirectory(path)` |
| 6 | `WorkspacePicker.tsx:127` `adoptDirectory` | 调 `createWorkspace({path})` |
| 7 | `workspace-controller/src/client/model.ts:85` `create()` | `await remote.create()` → **成功后 `this.upsert(...)`** |
| 8 | `model.ts:276` `upsert()` → `invalidate()` | ↓ **关键** |

#### 关键代码 `model.ts:315-332`

```ts
private invalidate(immediate = false): void {
  this.snapshotDirty = true
  this.notificationPending = true
  if (immediate) { ...; this.flush(); return }     // 立即路径
  if (this.notificationScheduled) return
  this.notificationScheduled = true
  const generation = ++this.notificationGeneration
  queueMicrotask(() => {                            // ← 唯一出口
    if (generation !== this.notificationGeneration) return
    this.notificationScheduled = false
    this.flush()                                    // ← 只有它通知订阅者
  })
}
```

**`flush()` 是通知 UI 订阅者的唯一出口，而它只在这个 `queueMicrotask` 回调里被调用。**

若该回调在异常期不执行：

| 现象 | 解释 |
| --- | --- |
| 工作区已创建、但列表不刷新 | `upsert` 改了内部 `items`，但**没通知订阅者**，React 不知道要重渲染 |
| **点任何地方就出现** | 任何输入都触发一次微任务检查点，**排队的回调终于跑掉** |
| 浏览器里秒完成 | 浏览器标签页是前台，微任务队列从不被压制 |
| R7 后渲染完全正常 | 渲染没问题，**是通知没发出去** —— 与 §3.12 完全一致 |

> **这条链能同时解释 C1（点哪都行）、C2（不点不出现）、C3（浏览器正常）、
> 以及 R7 之后渲染正常但现象依旧。是至今唯一做到这一点的假设。**

#### 但要警惕一个自相矛盾

`invalidate()` 里 `queueMicrotask` 是**标准微任务**，微任务在任何输入事件后都会跑，
**理论上不该被"冻结"**。所以还有两种可能，必须区分：

| 可能 | 说明 |
| --- | --- |
| **M-a** | 回调**确实排了但没跑**（微任务队列被压制）—— 现象最直接的解释 |
| **M-b** | 回调跑了，但 `generation !== this.notificationGeneration` **提前 return** 了（即后续有别的 `invalidate` 把 generation 顶掉，而那个新的又被 `notificationScheduled` 挡住）—— **逻辑竞态**，与窗口/渲染完全无关 |

**M-b 很有意思**：`if (this.notificationScheduled) return` 这行意味着
"已有排队的通知就不再排"，而 `notificationScheduled` **只在回调真正执行时才置回 false**。
若回调因 generation 过期而 return，`notificationScheduled` 已经被置 false 了——
但若**更早**某处让它停在 true 而回调永不执行，就会永久卡死。

⇒ **必须用探针区分 M-a 与 M-b**，这正是 R9 的 microtask 探针要做的。

### 3.14 R9 实测：**探针自激**，本轮作废（2026-09-12 15:48）

**结论先行：R9 探针有严重缺陷，没有产出任何有效数据。用户看到的现象是探针造成的。**

#### 用户报告

> 新开的 dshell 原有的工作区都没有了，点加工作区按钮也不好使了。

#### 真实原因：探针把自己吃掉了

新增的 line-1 `fetch` 包装拦截了**探针自己**向 `45789` 端口上报的请求，
而上报动作本身又是一次 `fetch` → 再次被拦截 → 再次上报……**无限自激**。

| 统计 | 数值 |
| --- | --- |
| `net:start` 总数 | **433** |
| 其中 url 指向探针端口 `45789` | **433（100%）** |
| 其中指向真实 dsh 后端 | **0** |
| `mic:` / `micro:` 输出 | **0 条** |

探针脚本在页面初始化时同步跑，第一条 `rec()` 就触发自激，
**在挂上 microtask / micro 健康探针之前**就把日志刷爆了。
所以本轮**既没有 microtask 数据，也没有网络数据**。

#### 数据是安全的（重要）

`%USERPROFILE%\.dsh\storages\workspace.json` **完好无损**（1171 字节，时间戳仍是 09:55，
即上一次成功运行时的状态）。两个工作区都在：

| path | title |
| --- | --- |
| `D:\Projects\dsh-shell` | dsh-shell |
| `D:\Projects\fpv-taobao` | fpv-taobao（测试时新增的那个） |

**"工作区都没有了"是显示层现象，不是数据丢失。**
真实原因：自激让主线程被 433 次 fetch 灌满，页面的 workspace 投影**没走完初始化**
（`phase` 停在 `pending`），列表因此是空的；`+` 按钮同样因为主线程被占而不响应。

> ⚠️ 教训（记为 **M6**）：**包装全局 API 的探针，必须排除自己的上报通道。**
> `fetch` 包装里第一步就该判断 `url` 是否指向探针端口，是则直接透传、不上报。
> 这是这一类探针的通用陷阱，之前几轮没踩到只是因为没包装过 `fetch`。

#### 待办

R9 需要修正后重跑：`fetch` 包装加自排除；`mic:` / `micro:` 探针**提到最前面**注册
（先于任何会 `rec()` 的东西），保证即使后续出事也能拿到核心数据。

#### 修正（已构建 `target-r9c`，2026-09-12 15:54）

三重防护，任一条都能单独断开自激回路：

| # | 措施 | 说明 |
| --- | --- | --- |
| 1 | **`post()` 固定持有原生 `fetch` 引用**（`nativeFetch = window.fetch.bind(window)`） | 从根上断开：上报永远走未被包装的版本，包装层根本看不到它。**比在包装里判断更可靠** |
| 2 | `fetch` 包装里 `isSelf(url)` **完全不记录**，直接透传 | 第二道防线（万一将来有人改回 `fetch`） |
| 3 | XHR 包装同样自排除 | 第三道防线 |
| 4 | **microtask 探针移到脚本最前面注册** | 教训 M7：核心判据必须最先注册 |
| 5 | 新增 `probe:selfcheck`（3 秒后上报一次） | 主动报告挂钩清单与 `netSeen` 计数，**让"探针自己坏了"一眼可见**（教训 M5） |

> `probe:selfcheck` 里 `netSeen=` 若异常大（成百上千），就是自激回来的信号。
> 正常情况它应该是个位数到几十。

而**探针自己的上报走的就是 fetch** —— 于是每一条上报都被 `PerformanceObserver`
再记一遍，与 §3.14 的自激同源（都是"没排除自己"）。

修正（`target-r9d`）：

1. `isSelf(e.name)` 排除探针自己的 origin
2. 只保留 `/api/` 路径 —— dsh 的业务请求全在这里，其余一律丢弃

> **教训 M8**：凡是"监听/记录网络"的探针，都必须同时排除自己的上报通道。
> 这与 M6 是同一类错误的两种表现（M6 包装 `fetch`，M8 监听 `resource`）。

#### 顺带确认的既有结论

| 事实 | 证据 |
| --- | --- |
| `pick` 的 `dur` 覆盖**整个对话框打开时长**（8026ms） | 证明该请求是长轮询式阻塞，不是"点确定才发请求" |
| Alt 在 `pick` 返回前 57ms 到达页面 | 与 §3.8 一致：Alt 由 dsh 合成、在对话框关闭时投递 |
| 工作区创建走 `POST /api/workspace/create`，耗时仅 210ms | **后端很快**，问题不在 Host |

## 9. R10：验证「幽灵点击」（2026-09-13）

### 9.1 假设

对话框关闭瞬间那条 `mousedown` 是**系统层注入的合成输入**，来源是 dsh 的
`pressAltForForeground()`（`host/directory-picker-native/src/win32-dialog-bindings.ts:148-151`）：

```ts
pressAltForForeground: () => {
  keybdEvent(VK_MENU, 0, 0, 0)            // Alt 按下
  keybdEvent(VK_MENU, 0, KEYEVENTF_KEYUP, 0)  // Alt 抬起
}
```

它在 `Show` **之前**执行（`win32-dialog-logic.ts:134`），目的是让这个进程
"最近有输入"，从而拿到前台权。而 `Show` 传的是 **`null` owner**
（`win32-dialog-logic.ts:135`、`bindings.ts:160`）：

```ts
show: () => method(dialog, SLOT_SHOW, protoShow)(null)
```

**没有 owner 意味着对话框与 DShell 主窗口之间没有 owner/owned 关系**，
激活态交接完全走前台队列。于是那次注入的输入会在交接瞬间落到 DShell 上。

### 9.2 判据：`isTrusted`

| 事实 | 含义 |
| --- | --- |
| `dispatchEvent` 造的假事件 → `isTrusted=false` | 页面脚本伪装的点击会被识破 |
| **`keybd_event` / `SendInput` 产生的是系统级真实输入** → `isTrusted=true` | 到达 Chromium 后与真实硬件输入**无法区分** |

所以：

| 观察 | 结论 |
| --- | --- |
| 对话框关闭瞬间有 `mousedown trusted=true`，而用户**手已离开键鼠** | ✅ **幽灵点击实锤**：系统层注入了输入 |
| 只有用户 5 秒后补点才有 `mousedown` | ❌ 本假设否证，回到页面层继续查 |

## 11. R11：方案 F1（壳层收回激活态）（2026-09-13）

### 11.1 依据

用户否证 C20：**"我不主动点鼠标/键盘 Alt/Shift，可能永远不能刷新。"**
复核数据证实（§10.7）：解冻（`.381`）**先于**幽灵点击（`.495`），刷新（`.866`）又在之后 371ms。
⇒ 幽灵点击**不是**唤醒机制，不能依赖它。

### 11.2 实现

新增 `src-tauri/src/focus_fix.rs`，在 `on_window_event` 里接 `WindowEvent::Focused`：

| 事件 | 动作 |
| --- | --- |
| `Focused(false)` | 记下墙钟时刻 |
| `Focused(true)` | 算 gap；**gap ≤ 1500ms** ⇒ 判定为对话框交接 ⇒ `set_focus()` 主动收回，并记日志<br>**gap > 1500ms** ⇒ 判定为用户切窗口 ⇒ **不干预**（避免把用户拽回来，见 04 §8 R3） |

| 设计决策 | 原因 |
| --- | --- |
| 用**时间窗**而非"是否在弹对话框" | Tauri 侧看不到 dsh 子进程弹对话框这个事实，唯一可得信号是窗口焦点事件 |
| 时间窗 **1500ms** | 对话框往返是秒级；用户切应用再切回通常远超之 |
| 只调窗口 `set_focus()`，**不**调页面 `window.focus()` | 后者会把 DOM 焦点抢到 body，可能干扰用户刚点进的输入框 |
| 收 `&AppHandle` 而非 `&WebviewWindow` | `on_window_event` 给的是 `Window`（**不是** `WebviewWindow`），类型上只有前者可行（首次构建即撞到此错） |
| 只处理 `MAIN_WINDOW` | 将来做设置窗口时，它的焦点事件不该触发本修复 |

## 13. R11-c：把时钟搬到 Rust 侧（用户提案，2026-09-13）

### 13.1 用户的判断（正确）

> 现在卡住的应该是前台 web 吧？Rust 侧应该是没被卡住。
> 所以，要不要在前台加消息通讯给后台呢，比如那几个关键动作的时刻。

**数据支持这个判断**：同一份日志里，Rust 墙钟 `[HH:MM:SS.mmm]` 一直在走，
而页面 `t=`（`Date.now()`）在 15.2 秒里**纹丝不动**。
⇒ **冻的是页面，Rust 一直在跑。**

### 13.2 为什么这是必需的

页面冻结时，它的 `Date.now()`、`setInterval`、`MutationObserver` **全部停摆**
—— 那 15 秒在**页面侧是盲区**。而 Rust 侧一直清醒。

所以任何"跨越冻结期"的因果判断，**必须有一个 Rust 侧的锚点**，否则接不起来。

### 13.3 新增的三路 Rust 侧数据

| # | 打点 | 格式 | 回答什么 |
| --- | --- | --- | --- |
| 1 | 关键动作 | `[HH:MM:SS.mmm] rust: <what>` | 窗口失焦/复焦、探针启动等，**独立于页面** |
| 2 | **心跳到达** | `HBARRIVAL` + `rxn=N` | **页面活过来的精确时刻**（Rust 测的） |
| 3 | **包间隔异常** | `RUSTGAP=<ms>` | 间隔 >3.5s ⇒ 中间冻过一次，**冻结时长直接可读** |

其中 **#2 是核心**：页面每 2 秒发一次心跳，Rust 记录**收到**的墙钟。
冻结期间收不到，解冻后一次性涌进来 —— **那批包的到达时刻就是"页面活过来"的时刻**，
且**不受页面时钟停摆影响**。

### 13.4 两组时钟如何对齐

| 侧 | 字段 | 含义 | 冻结期间 |
| --- | --- | --- | --- |
| 页面 | `t=` | 消息**产生**的时刻 | ❌ 不推进 |
| Rust | `[HH:MM:SS.mmm]` | 消息**收到**的时刻 | ✅ 一直准 |

拼起来即可回答那个唯一重要的问题：

```
Rust: 最后一条心跳到达     = T1   （页面从此冻死）
Rust: focus=LOST / GAINED  = T2   （窗口激活态变化）
Rust: RUSTGAP              = Δ    （冻结时长）
页面: kind=mut sinceDown   = d    （点击 → DOM 更新的真实延迟）
```

**若 `kind=mut` 的 `sinceDown` 很小（几十 ms）⇒ 是点击触发的刷新，F1 没用。
若它很大或该次点击后没有变异 ⇒ 页面自己刷的。**

| 项 | 值 |
| --- | --- |
| 产物 | `src-tauri\target-r11c\release\dshell.exe`（3,503,104 B） |
| 构建结果 | ✅ 零错误零警告 |

```
                 ⋯ 页面冻结 11.747 秒（RUSTGAP=11747 实测）⋯
08:58:17.221  kup key=Alt  RUSTGAP=11747           ← Alt-up 投递，页面解冻
08:58:17.226  hb ticks=48 ⋯ ticks=88（6 条补发）   ← 解冻确认
08:58:17.260  down hit=div.wSkVaW_composerStack    ← 用户读秒读完，点了一下
08:58:17.263  mut  sinceDown=1                     ← DOM 更新，距那次点击 1 毫秒
```

**`sinceDown=1ms` 是铁证**：DOM 更新恰好发生在用户点击后 **1 毫秒**。
若刷新是页面自己产生的，不可能卡在这个位置。

⇒ **用户报告的"必须点一下才刷新"已被完全证实。**

### 14.2 关键区分：**解冻 ≠ 刷新**

| 时刻 | 事件 |
| --- | --- |
| 08:58:17.221 | 页面**解冻**（心跳恢复、时钟开始走） |
| 08:58:17.221–17.260 | **39ms：页面活着，但什么都不画** |
| 08:58:17.260 | 用户点击（一次真实输入事件） |
| 08:58:17.263 | DOM 更新（+1ms） |

**页面在解冻后是"活的僵尸"**：定时器跑、时钟走、能收事件，但**不提交渲染**。
只有一次真实输入才让它提交 —— 与 dsh `model.ts:315-332` 的 `queueMicrotask` 出口吻合
（§3.13）：`notificationScheduled` 卡在 `true`，后续 `invalidate()` 全被吞，
需要一次输入推动微任务检查点。

### 14.3 前三轮的错误结论（全部作废）

| 轮次 | 当时的结论 | 实际 |
| --- | --- | --- |
| R10 | "幽灵点击" | ❌ 那些 `down` 都是**用户的真实点击** |
| R11 | "界面自己刷新了，比补点早 798ms" | ❌ **1 秒采样粒度**造成的假象 |
| R11 | "F1 可能有效" | ❌ F1 完全无效 |

**根因是探针分辨率**：`changed` 基于每秒采样，最多只能说"变化在两次采样之间"。
换成 `sinceDown`（毫秒级）后，答案立刻出现。

## 15. R13：为什么快 20 轮都抓不到「对话框关闭」

### 15.1 用户的提问

> 其实还是没抓到对话框关闭的事件，两个时间段（选文件夹 / 关闭后读秒）还是没分开。
> 为啥快 20 轮了一直抓不到那个事件。

### 15.2 答案：**那一刻页面是死的，而事件不在页面侧**

冻结窗口内的原始日志（`08:58:05.474` → `08:58:17.221`）：

```
08:58:05.474  kdn key=Alt          ← 冻结前页面的最后一条
                 ⋯ 11.747 秒，Rust 侧收不到页面的任何消息 ⋯
08:58:17.221  kup key=Alt          ← 解冻后第一条
```

**对话框关闭（用户点「选这个目录」）发生在这 11.7 秒中间的某一刻**，但当时：

| 手段 | 为什么抓不到 |
| --- | --- |
| 页面 `mousedown` 监听 | ❌ 用户点在**对话框**上，事件根本不到页面；且页面冻着不跑监听器 |
| 页面 `blur` / `focus` | ❌ 页面冻着，处理不了 |
| 页面时钟 `Date.now()` | ❌ 停摆（`kdn` 与 `kup` 的 `t` 完全相同） |
| `setInterval` 心跳 | ❌ 定时器停摆，消息发不出去 |
| **Windows 窗口消息钩子**（R8） | ❌ `winmsg` 全空 —— 对话框窗口属于**子进程**，不在我们线程的消息队列里 |
| **Rust 的 `Focused` 事件** | ⚠️ 只报 `gap=2ms`，与实际 11.7 秒完全不符 |

### 15.3 症结：只有"回声"，没有"事件"

冻结结束时的信息**全部挤在一起到达**：

```
08:58:17.221  kup key=Alt     ← 这不是"对话框关闭"，只是"被扣押的东西终于投递"
08:58:17.226  hb ticks=48     ← 补发第 1 条
08:58:17.241  hb ticks=88     ← 补发第 6 条
```

`kup` 与真正的"对话框关闭"相差多远，**从页面侧永远测不出来** ——
因为分开它们所需的信息，不在已采集的任何一条通道上。

### 15.4 出路：看**进程**，不看页面/窗口

每条通道都不行，只剩一个位置从没查过 —— **进程层**。

读 `win32-dialog-host.ts:24-32` 得知：对话框在 dsh 的**独立 node 子进程**里打开并阻塞：

```ts
spawn(process.execPath, ['--import', <tsx>, '.../win32-dialog-worker.ts'], …)  // 源码面
spawn(process.execPath, ['.../worker.cjs'], …)                                 // 构建面
```

| 观察 | 含义 |
| --- | --- |
| worker 进程**出现** | 对话框正在打开 |
| worker 进程**消失** | **对话框已关闭** ← 20 轮一直缺的那个时刻 |

**全在 Rust 侧，不受页面冻结影响。**

### 15.5 API 选择的踩坑记录

先试了三条路，**都不可用**（本机实测）：

| 方案 | 结果 |
| --- | --- |
| `wmic process get CommandLine` | ❌ `Alias not found`（本机 wmic 已废） |
| `Get-CimInstance Win32_Process` | ❌ 拒绝访问（需提权） |
| `tasklist /V` | ❌ Access denied |

⇒ 只有 **Toolhelp32 快照**（`CreateToolhelp32Snapshot`）无权限要求、
一次调用拿全进程表**含父 PID**。识别 worker 用**父进程匹配 dsh pid**
（而非读命令行 —— 那要 `ReadProcessMemory` 跨进程读 PEB，重且易碎）。

### 15.6 实现与构建

| 项 | 值 |
| --- | --- |

| 依赖 | `windows-sys 0.61`（仅 `Win32_System_Diagnostics_ToolHelp` + `Win32_Foundation`） |
| 轮询间隔 | 250ms |

| 构建结果 | ✅ 零错误**零警告** |
| 二进制校验 | `dialogwatch: started` / `rust: dialog=OPEN` / `rust: dialog=CLOSE` / `open_for` ✅ FOUND |

**新增日志（Rust 侧，冻结期间也有）**：


有了 `dialog=CLOSE`，时间线终于能切成两段：

## 17. R15：**换掉对话框本身** —— 最终解法（2026-09-13）

### 17.1 转折点：用户问"根目录下有 dsh 源码，你看了吗"

前 20 多轮一直在**症状层**搏斗（冻结 → 通知 → 微任务 → 幽灵点击），
**从未问过：为什么 Windows 上必须用原生对话框？**

读 `packages/host/directory-picker-auto/src/resolve.ts:50-52` 得到答案：

```ts
if (facts.bindHost !== '127.0.0.1') return 'browse'
if (facts.ssh) return 'browse'
if (facts.platform === 'darwin' || facts.platform === 'win32') return 'native'  // ← 无条件
```

**win32 + loopback ⇒ 必然 native** ⇒ 必然"另一个进程弹模态窗口"⇒
必然失焦 ⇒ 必然挂起 11.7 秒。

### 17.2 dsh 官方支持覆盖它

`packages/bundle/web-app/cordis.patch.yml:94-96` 在该行上方的注释原文：

> Resolve bind host, SSH launch, and display once at boot, then mount the matching
> dual-face directory picker. **Mount `-native` or `-browse` directly in an overlay
> to pin the interaction.**

`-browse` 是 dsh 官方实现的**应用内网页对话框**：它就在页面里，
不存在另一个进程的窗口盖上来 ⇒ 页面不失焦、不挂起，
且对话框的开关**天然在页面 JS 里可见**（20 轮没抓到的那个事件自动到手）。

### 17.3 改动（用户级配置，**不改 dsh 源码**）

文件 `%USERPROFILE%\.dsh\profiles\web\cordis.patch.yml`（原内容仅 `[]`）：

```yaml
- id: directory-picker
  disabled: true

- insert:
    - id: directory-picker-browse
      name: '@deepseek-ai/dsh-host-directory-picker-browse'
    - id: directory-picker-browse-surface
      name: '@deepseek-ai/dsh-client-ui-directory-picker-browse'
```

| 项 | 值 |
| --- | --- |
| 依赖 | 两个包在 `dsh@0.1.5-rc.1` 中**已随包安装**，无需另装 |
| 备份 | 原文件已存为 `cordis.patch.yml.bak-original` |
| YAML 校验 | ✅ 用 dsh 自带的 `yaml` 库解析成功，结构为预期的两元素数组 |
| 修改时间 | 2026-09-13 10:4x |

### 17.4 实测结果：**挂起消失，但候选方案被用户否决**

| 观察 | 结果 |
| --- | --- |
| 是否变成网页内对话框 | ✅ **是**（用户实测确认） |
| 是否还挂起 | ✅ **不再挂起**（结构性问题消失） |

## 18. R16：横向参考 —— DSH Desktop 怎么做的（2026-09-13）

### 18.1 项目

| 项 | 值 |

本地 clone：`D:\Projects\dsh-shell\src-of-dsh-desktop`（`--depth 1`，32.5 MB）。

### 18.2 **他们的做法：自己弹原生对话框**

关键文件 `dsh-plugin-desktop/src/`：

| 文件 | 作用 |
| --- | --- |
| `directory-picker-contract.ts` | 定义同源端点 `/_dsh/desktop/pick-directory` |
| `directory-picker-route.ts` | 该端点的 HTTP 处理器（校验 origin、只收 POST） |
| `directory-picker.ts` | 页面侧调用端点的封装 |
| `workspace-admission.ts:90-96` | **真正弹对话框的地方** |
| `electron-shell-generation.ts` | **把主窗口设为对话框的 parent** |

**核心代码**（`workspace-admission.ts`）：

```ts
const result = await this.options.showOpenDialog({
  title: locale === 'zh' ? '选择工作区目录' : 'Select Workspace Directory',
  properties: ['openDirectory', 'dontAddToRecent'],
})
return result.canceled ? null : result.filePaths[0] ?? null
```

**主窗口作为 parent**（`electron-shell-generation.ts`）：

```ts
async showOpenDialog(options) {
  const window = this.window
  return window === undefined || window.isDestroyed()
    ? await dialog.showOpenDialog(options)
    : await dialog.showOpenDialog(window, options)   // ← 关键：传了 window
}
```

**架构**：

```
页面（dsh 的 browse 面板，Windows 上）
   │  点「原生选择器快捷方式」按钮
   ↓
POST /_dsh/desktop/pick-directory        ← 同源 HTTP 端点
   ↓
Electron 主进程 → showOpenDialog(window, …)   ← 自己进程的对话框，主窗口为 parent
   ↓
返回 { path }
```

还配套了 `/_dsh/desktop/validate-directory` 与 `windows-volume-diagnostics.ts`
（查 NTFS/ReFS、可移除磁盘警告）。

### 18.3 **为什么他们不挂起、我们挂起**（关键对比）

| | DSH Desktop（Electron） | DShell（Tauri，现状） |
| --- | --- | --- |
| 对话框由谁弹 | **Electron 主进程**（自己进程） | dsh 的**独立 node 子进程** |
| owner / parent | ✅ `showOpenDialog(window, …)` | ❌ **`Show(null)` 无 owner** |
| 主窗口失焦 | ❌ **不会** | ✅ **会** |
| 页面挂起 | ❌ 不会 | ✅ **11.7 秒**（实测） |
| 盘符导航 | ✅ 原生对话框自带 | ✅ 原生对话框自带 |

> **结论：dsh 的 `-native` 后端本身没问题，问题在于"谁弹这个对话框"。**
> 另一个进程弹的无 owner 窗口 ⇒ 必然抢前台 ⇒ 必然失焦 ⇒ 必然挂起。

### 18.4 **Tauri 同样可行**（已验证可行性，未实现）

| 要素 | DSH Desktop | DShell 对应物 |
| --- | --- | --- |
| 原生对话框 | Electron `dialog.showOpenDialog` | `tauri-plugin-dialog`（**已装**：`Cargo.toml` 里有 `tauri-plugin-dialog = "2"`） |
| **能否设 parent** | ✅ 传 `window` | ✅ **`set_parent(&window)`**（`tauri-plugin-dialog-2.7.3/src/commands.rs:130, 230, 282`） |
| 端点 | 同源 `/_dsh/desktop/pick-directory` | Rust 侧自建同源端点（或 Tauri `invoke`） |
| 页面侧接管 | browse 面板加"原生选择器"按钮 | **注入脚本劫持 `pick`**（`initialization_script` **已证可用**，§16） |

⇒ **两个关键前提都已落实**：
1. Tauri 的对话框支持指定 parent ⇒ **不会让主窗口失焦**
2. 我们有可用的页面注入通道 ⇒ **能把 dsh 的 `pick` 重定向到我们的端点**

### 18.5 与 dsh 官方 seam 笔记的吻合

`directory-picker` 的架构笔记（2026-07-28）早就预告了这个用法：

> **native 后端保留。** 插件化正是目的：多个提供方都能提供该 seam
> （**Electron 壳可以经自己的对话框 API 提供 `native` 交互**）。

**DSH Desktop 实现的正是这句话。** 我们要做的是它的 Tauri 版本。

## 19. R17–R19：**注入两条通道都是死的** ⇒ 改走 dsh 插件机制（2026-09-13 晚）

### 19.1 结论先行

| # | 问题 | 结果 |
| --- | --- | --- |
| 1 | `initialization_script` 能用吗 | ❌ **不能**。脚本第一行的 `sendBeacon` 一次都没到 |
| 2 | `eval` 能用吗 | ❌ **不能**。`eval` 返回 `Ok(())`（仅表示**入队**），页面零回传 |
| 3 | 那怎么办 | ✅ **不走注入**，改用 dsh 官方的插件机制（下文） |

**§16 的"注入可用"是误判**，病根见 §16 开头更正的方框。

### 19.2 为什么 `eval` 的 `Ok(())` 会骗人（教训 M13）

R11-c 记过"`eval` 在页面冻死时排队而非报错"，但只当成"不能用返回值判断页面活着"。
**真正的结论更强**：`eval` 的返回值**任何情况下都不代表代码执行了**。
本轮用它测注入通道，三个 `eval` 全返回 `Ok(())`、页面零回传——
如果只看返回值，会再次得出"注入可用"的错误结论。

> **教训 M13：`eval` 的 `Ok(())` 只说明"排进了队列"。要判断代码有没有执行，
> 必须让页面**从另一条通道**（`sendBeacon`）回报。**

### 19.3 解法：把交互后端换成一个 dsh 插件

前 20 轮的死结是"**页面里没有我们的代码**"。既然注入进不去，
就**不注入**——改在 dsh 的 **host 进程**里动手。dsh 把"怎么选目录"做成了
capability seam（`@deepseek-ai/dsh-host-directory-picker`），
后端只是一个实现了 `capability()` 的类，所以可以整体换掉：

```
dsh host 进程                          DShell 进程
─────────────                          ────────────
dshell-directory-picker
  pick(signal)
    └── POST /_dsh/desktop/pick-directory ──► 原生对话框（set_parent 有 owner）
    ◄──────────── {"path": "..." | null} ─────┘
```

**这完全走在 dsh 官方插件机制里**：不注入、不改 dsh 源码，
dsh 自己按 `dsh.profile.bundles` 加载它。

### 19.4 与 DSH Desktop 的逐项对应

| | DSH Desktop（Electron） | DShell |
| --- | --- | --- |
| 谁弹框 | Electron 主进程 | Rust 进程（Tauri） |
| parent | `showOpenDialog(window, …)` | `set_parent(&window)` → rfd `Show(hwnd)`（`tauri-plugin-dialog-2.7.3/src/commands.rs:130`） |
| 通道 | `/_dsh/desktop/pick-directory` | 同路径、同响应体 `{path: string \| null}` |
| dsh 侧接入 | 打补丁的 browse 面板 | **dsh 插件**（我们不改 dsh，所以走它自己的插件机制） |

第 4 项是唯一的形式差异，**原因是 DShell 不能改 dsh 源码**（薄壳红线）；
达到的效果相同。

### 19.5 关键实现约束

| 约束 | 为什么 |
| --- | --- |
| 插件**不能**再 provide 一次 `directoryPicker` | `reflect.provide` 对重复注册**抛错**；且 `reflect.set` 要求同 fiber，改不了别人的实现 |
| 所以改写**已有实例的 `capability()`** | 消费方只读这一个方法；服务所有权、生命周期、依赖关系全不动 |
| patch 层**不许禁用** dsh 的 `directory-picker` 行 | 一旦插件因故不动作，就会**一个后端都没有** ⇒ 「添加工作区」按钮消失（**真踩过**） |
| 拿不到 `DSHELL_PICKER_PORT` 时必须**完全不动作** | 普通 `dsh web`（终端直接跑）不能用坏 |
| 端点用**共享令牌**而非 `Origin` 同源校验 | 调用方是 dsh 的 host 进程（Node `fetch`），**不发 `Origin`** |

### 19.6 实测结果（2026-09-13）

| 验证 | 结果 |
| --- | --- |
| 插件注册为 `directoryPicker`，kind=`native` | ✅ 客户端完全无感 |
| `pick()` 发出 HTTP 到 DShell 端点 | ✅ |
| 令牌校验（无令牌 403） | ✅ |
| 无 `DSHELL_PICKER_PORT` 时不影响内置 picker | ✅ |
| **端到端：点「添加工作区」→ 不失焦、不挂起、自动刷新** | ✅ **用户实测通过** |

DShell 侧日志 `picker: bridge listening on 127.0.0.1:53415` 与插件侧
拿到的端口一致，证明两端真的接上了。
